# Security Testing Hub

> 🇰🇿 Қазақша нұсқа: жалпы құжаттама әзірге жоқ, бірақ шабуылдарды тестілеу
> нұсқаулығы бар — [attack-playbook.kk.md](attack-playbook.kk.md).

Открытый SAST-сканер для тех, кто пишет Node.js/Express-приложения быстро,
часто с помощью AI-ассистентов ("vibe coding"), и не всегда успевает
проверить каждую строчку на классические уязвимости.

## Зачем это нужно

AI-ассистенты быстро генерируют рабочий код, но часто воспроизводят одни и
те же уязвимости внедрения (SQL-запросы через конкатенацию строк,
неэкранированный вывод в HTTP-ответ, `exec()` с подставленным вводом) —
просто потому что такие паттерны часто встречаются в обучающих данных.
Этот инструмент — быстрая локальная проверка (pre-commit/CI), заточенная
именно под паттерны, которые чаще всего появляются в "вайбкодинговых"
Express-приложениях.

## Что находит (v1 / MVP)

| Уязвимость | CWE | Как ищем |
|---|---|---|
| SQL Injection | CWE-89 | taint-анализ вызовов `db.query`/`execute`/`knex.raw` |
| XSS (отражённый) | CWE-79 | taint-анализ `res.send`/`write`/`end` |
| Command Injection | CWE-78 | taint-анализ `child_process.exec`/`execSync` |
| Path Traversal | CWE-22 | taint-анализ вызовов `fs.*` |
| SSRF | CWE-918 | taint-анализ `fetch`/`axios`/`http(s)`/`request`/`got` |
| CSRF | CWE-352 | эвристика по роутам (нет проверки токена) |
| IDOR | CWE-639 | эвристика по роутам (id-параметр без проверки владения) |
| Broken Access Control | OWASP A01:2021 | эвристика по роутам (admin-путь без проверки роли) |
| Insecure Role Assignment | CWE-639 | паттерн (роль читается из клиентских данных) |
| Insecure File Upload | CWE-434 | паттерн (фильтр загрузки доверяет только Content-Type) |
| Username Enumeration | CWE-203 | паттерн (разные сообщения об ошибке логина) |

Подробный разбор всех 15 классов атак (что это, как проверить руками,
как защититься) — в [attack-playbook.ru.md](attack-playbook.ru.md).

## Как это работает

1. **Парсинг** — каждый `.js`/`.jsx`/`.ts`/`.tsx` файл парсится в настоящий
   AST через Tree-sitter (не регулярки).
2. **Taint-анализ** — для пяти правил, основанных на потоке данных,
   анализатор находит "источники" (`req.params`, `req.query`, `req.body`, ...),
   отслеживает их через локальные переменные и интерполяцию в
   template-строках, а если значение передаётся в другую функцию (в том же
   файле или в другом) — следует за ним туда (`routes` -> `services` -> `db.query`),
   и проверяет, попадает ли tainted-значение в опасный "sink"
   (`db.query`, `res.send`, `exec`, `fs.readFile`, ...).
3. **Отчёт** — результат в виде цветного текста в терминале, JSON или
   SARIF (для GitHub code scanning).

## Веб-интерфейс (без терминала)

```bash
npx security-hub ui            # откроет http://127.0.0.1:4173 в браузере
npx security-hub ui ./my-app   # то же, сразу с нужной папкой
```

Выберите папку проекта (или вставьте путь), нажмите **Сканировать** — появятся
оценка 0–100, находки с фильтром по важности и кнопка скачивания HTML-отчёта.
Интерфейс доступен на английском, русском и казахском. Всё работает на вашем
компьютере: сервер слушает только `127.0.0.1`, каждый запрос защищён токеном, код
никуда не отправляется.

## Supabase и Firebase

Для проектов на Supabase и Firebase главная защита — не код, а **правила доступа**, а публичный ключ приложения виден
каждому в браузере. Поэтому сканер читает SQL-миграции Supabase (`supabase/migrations/*.sql`) и файлы правил Firebase
(`firestore.rules`, `storage.rules`, `database.rules.json`):

- **Supabase:** таблица без Row Level Security, политика `USING (true)`, «вошёл в систему» вместо проверки владельца,
  роль из `user_metadata` (пользователь меняет её сам), вьюха без `security_invoker`, `SECURITY DEFINER` без
  `search_path`, открытые политики хранилища; в коде — `getSession()` на сервере без проверки и роли из `user_metadata`.
- **Firebase:** `allow read, write: if true`, «тестовый режим» консоли (`request.time < timestamp.date(...)`),
  `request.auth != null` как единственная проверка записи, открытые приватные пути в Realtime Database.
  Ключ service account (`*-firebase-adminsdk-*.json`) в репозитории — критичная находка.

Читает именно миграции, а не живую базу: что исправлено только в панели Supabase и не попало в миграцию, будет
показано как проблема. Подробности — в `docs/rules.md`.

## GitHub Action (проверка каждого pull request)

```yaml
# .github/workflows/security.yml
on: pull_request
permissions: { contents: read, pull-requests: write }
jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: dam1r-dev/security-testing-hub@v0
        with: { fail-on: high }
```

В pull request показываются **только находки в изменённых файлах**: аннотации прямо в диффе, один комментарий
с оценкой 0–100 (обновляется при каждом push) и сводка задачи. Проект при этом анализируется целиком, поэтому
изменённый обработчик, передающий данные в нетронутую функцию запроса, всё равно будет найден. Подробности —
[docs/github-action.md](github-action.md). В командной строке то же самое:
`security-hub scan . --changed-since origin/main`.

## Секреты в коде (`hardcoded-secret`)

Находит ключи и пароли, оставленные в исходниках: токены известных сервисов (AWS, GitHub, Stripe, OpenAI/Anthropic,
Slack, Supabase `service_role`, приватные ключи, адреса БД с паролем), угадываемые секреты `jwt.sign` и `session`
(`"secret"`, `"keyboard cat"`), пароли и ключи по имени переменной, секреты за «публичными» префиксами
(`NEXT_PUBLIC_…_SECRET` попадает в браузер каждого посетителя) и файлы `.env`, закоммиченные в git или не
добавленные в `.gitignore`. **Найденный секрет нигде не показывается целиком** (ни в консоли, ни в HTML, ни в
комментарии PR): только узнаваемое начало. В каждом сообщении сказано: считай ключ утёкшим, перевыпусти его —
удалить строку недостаточно, значение остаётся в истории git.

## Промпт для ИИ-ассистента

К каждой находке есть готовый промпт для Cursor / Claude / Copilot: файл и строка, в чём проблема, код, как
исправить, требования («меняй только нужное, покажи diff»). В веб-интерфейсе и HTML-отчёте — кнопка
**«Скопировать промпт для ИИ-ассистента»** у каждой находки и одна общая; в комментарии PR — свёрнутый блок;
в консоли — `security-hub scan . --format prompt`. Секреты в промпт не попадают.

## Как скрыть неверную (или принятую) находку

```js
// security-hub-ignore -- внутренний инструмент, вход приходит из подписанной задачи
db.query("SELECT * FROM jobs WHERE id = " + jobId);

db.query(sql); // security-hub-ignore sql-injection
```

- Комментарий ставится **на строке с находкой или на строке прямо над ней**. Без названий правил
  скрывает все находки на этой строке; `security-hub-ignore xss, sql-injection` — только эти правила.
  Текст после `--` — произвольная причина. В отчёте всегда указано, сколько находок скрыто.
- Целые файлы и папки: файл **`.security-hub-ignore`** в сканируемой папке (по одному шаблону в строке,
  `#` — комментарий) или ключ `--ignore <шаблон>` (можно несколько раз). Шаблоны — упрощённый `.gitignore`.
- Папки тестов (`test`, `tests`, `__tests__`, `e2e`, ...) и файлы `*.test.*` / `*.spec.*` по умолчанию
  пропускаются; `--include-tests` включает их в скан.

## Ограничения (честно, как в плане разработки)

- **Только JavaScript/TypeScript.** Python и PHP — после MVP.
- **Taint идёт по вызовам, но не по возвращаемым значениям.** Данные запроса
  отслеживаются через локальные переменные, деструктуризацию и шаблонные строки, а
  также **внутрь** функций проекта, в которые они передаются — между файлами, через
  `require`/`import` (в том числе алиасы `@/` и `paths` из tsconfig), объекты, классы,
  функции-конструкторы и `this.method()`, до шести вызовов в глубину. Не отслеживается:
  данные, **возвращённые** из функции (`const q = buildQuery(x); db.query(q)`),
  колбэки, значения в полях объектов, DI-контейнеры и динамический `require`.
  Значение, обёрнутое вызовом (`parseInt(x)`, `sanitize(x)`), считается очищенным.
  Что сканер не смог определить — он пропускает: ошибка здесь — пропущенная находка,
  а не выдуманная.
- **Целевой False Positive Rate: 25–30%**, False Negative Rate: <10%. Для
  сравнения: у Snyk ~15–20% FP, у SonarQube ~20–30% FP — результат
  v1-инструмента соло-разработчика в этом диапазоне честен, а не является багом.
- **CSRF-проверка эвристическая**, не taint-based: помечает
  state-changing роуты (`POST`/`PUT`/`DELETE`/`PATCH`) в файлах без
  видимой CSRF-защиты. Предполагает cookie/session-аутентификацию.
